# catch-up

## 触发场景
- 项目首次建立文档体系
- 其他开发者修改了代码但没更新文档
- 切换到新分支后文档缺失或不匹配
- 长时间未维护文档后恢复

## 执行步骤

### 1. 扫描现状

- 运行 `git log --format="%ai %H %s" -20` 获取近期提交（含精确北京时间）
- 如有已提交的历史：`git diff HEAD~N --stat` 查看变更范围
- 遍历项目源码目录，读取关键代码文件
- 读取现有 `record/project/features/` 文件（如有），对比代码实际情况

### 2. 划分功能边界

按**逻辑功能**划分，而非按文件划分。

划分原则：
- 一个功能 = 一组协同完成同一职责的代码，可以跨多个文件
- 一个文件也可以属于多个功能（如一个文件中包含多个独立职责）
- 粒度标准：**会被独立修改、独立测试、独立讨论**的最小逻辑单元
- 避免过细（每个文件一个功能）或过粗（整个项目一个功能）
- 如果两块代码总是一起改，合为一个功能

示例：
- ✅ "预测模型层"（包含 3 个模型文件 + embedding 层）= 1 个功能
- ✅ "数据管道"（数据加载 + 工厂 + 时间编码）= 1 个功能
- ❌ "DLinear.py" = 1 个功能（太细，除非它有独立的迭代生命周期）
- ❌ "整个 forecast/" = 1 个功能（太粗）

### 3. 识别差异

对每个功能：
- 代码有变更但 feature 文件未更新 → 需要 catch-up
- 新增了代码但无对应 feature 文件 → 需要新建
- feature 文件描述的功能已被删除 → 标记为弃用
- 已有 feature 文件内容与代码一致 → 跳过

### 4. 生成/更新功能详情文件

对每个需要处理的功能，读取源代码后按以下模板生成 `record/project/features/fXX-kebab-name.md`：

```markdown
# [FXX] 功能名称

## 状态

- **实现状态**：✅已完成 / 🔧进行中 / 📋计划中 / ❌已废弃
- **核心文件**：
  - `path/file.py:行号` — 类名/函数名，职责描述
  - （一个功能可以包含多个文件，全部列出）
- **功能描述**：当前功能做什么，怎么做。从源码中提取，不要猜测。
- **测试方法**：可执行的测试命令或代码片段。（根据功能特性设计）

## 变化

### [实现] YYYY-MM-DD HH:MM — 初始实现 (`commit_hash`)

<details><summary>详情</summary>

**计划**：功能目标和技术方案
**代码修改**：新增了哪些文件/类/函数
**测试**：
| 方法 | 结果 | 备注 |
|------|------|------|
| （暂无记录） | | |

**已知问题**：
- 问题描述 — 优先级

</details>
```

### 5. 生成/更新索引文件

更新 `record/project/index.md`，包含：

**架构概览**：一段简要描述 + 层次图。

**功能清单表**（增量更新，不重新生成已有行）：

| ID | 功能 | 核心文件 | 最初实现 | 最后变更 | 状态 | 维护 | 详情 |
|----|------|----------|----------|----------|------|------|------|

核心文件列：列出功能涉及的主要文件/目录（多个用逗号分隔）。

状态图例：
- ✅无误 / ⚠️有注意事项 / 🔴有Bug
- 🟢在用 / 🟡冻结 / 🔴弃用

**全局问题汇总表**：从 features/*.md 的已知问题中聚合，加链接到来源功能文件，不单独编写。

### 6. 提交

```bash
git add record/
git commit -m "docs(catch-up): 同步文档至当前代码状态"
```

## 格式约定

- 所有时间戳使用北京时间 (UTC+8)，格式 `YYYY-MM-DD HH:MM`
- 使用 `git log --format="%ai %s"` 获取精确 commit 时间
- 不要猜测实现细节，直接读源码
- 功能 ID（FXX）递增分配，读取 index.md 当前最大 ID 后 +1
- 文件名用 kebab-case：`fXX-kebab-name.md`
- index.md 日期列简写：`MM-DD HH:MM`
- 变化条目按时间倒序排列（最新在上）
- 用 `<details><summary>` 折叠详情内容
