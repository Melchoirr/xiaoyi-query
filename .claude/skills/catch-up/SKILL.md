# 文档追赶流程

## 触发场景
- 项目首次建立文档体系
- 其他开发者修改了代码但没更新文档
- 切换到新分支后文档缺失或不匹配
- 长时间未维护文档后恢复

## 执行步骤

### 1. 扫描现状
- `git log --format="%ai %H %s" -20` 获取近期提交
- 遍历项目源码目录，读取关键代码文件
- 读取现有 `record/project/features/` 文件（如有），对比代码实际情况
- 参考 `record/project/workflow.md` 了解文档体系规范

### 2. 划分功能边界
按**逻辑功能**划分（参考 workflow.md 第五节）：
- 一个功能 = 一组协同完成同一职责的代码，可跨多个文件
- 粒度：会被独立修改、独立测试、独立讨论的最小逻辑单元
- 避免过细（每个文件一个功能）或过粗（整个项目一个功能）

### 3. 生成/更新功能详情文件

对每个功能生成 `record/project/features/fXX-kebab-name.md`：

```markdown
# [FXX] 功能名称

## 状态

- **实现状态**：✅已完成 / 🔧进行中 / 📋计划中 / ❌已废弃
- **核心文件**：
  - `path/file.py:行号` — 类名/函数，职责描述
  - （一个功能可包含多个文件，全部列出）
- **功能描述**：当前功能做什么，怎么做。从源码中提取，不要猜测。
- **测试方法**：可执行的测试命令或代码片段。

## 变化

### [实现] YYYY-MM-DD HH:MM — 初始实现 (`commit_hash`)

<details><summary>详情</summary>

**计划**：功能目标和技术方案
**代码修改**：新增了哪些文件/类/函数
**测试**：
| 方法 | 结果 | 备注 |
|------|------|------|
| （暂无） | | |

</details>
```

### 4. 生成/更新索引文件

更新 `record/project/index.md`：
- 架构概览（简要描述 + 层次图）
- 功能清单表（增量更新，不重新生成已有行）：

| ID | 功能 | 核心文件 | 最初实现 | 最后变更 | 状态 | 维护 | 详情 |
|----|------|----------|----------|----------|------|------|------|

- 全局问题汇总表

### 5. 提交
```bash
git add record/
git commit -m "docs(catch-up): 同步文档至当前代码状态"
```

## 注意事项
- 所有时间戳使用北京时间 (UTC+8)
- `git log --format="%ai %s"` 获取精确 commit 时间
- 不要猜测实现细节，直接读源码
- 功能 ID（FXX）递增，读 index.md 当前最大 ID 后 +1
